QA流程复盘与轻量测试台账方案

案例：VIP管理 / 查看会员 / 成员数量 输出：HTML 日期：2026-07-08
流程沉淀

这次流程的收益

环节 做对的地方 继续坚持
需求拆解 从 Lark 任务、Axure、后台现状里抽出了真正的验收对象：入口、列表顺序、成员数量、弹框、0 数量规则。 每个需求先做“需求点总结”，不要直接写测试步骤。
需求疑问 后来根据产品补充，把问题收敛到产品已确认的规则上，避免继续问泛化问题。 只问会影响验收口径的问题；文档已有说明的不重复问。
执行验证 按明确规则继续实测，发现了两个可交付给开发的问题。 执行时优先验证产品明确规则，发现问题必须有步骤、实际、期望和截图。
证据沉淀 最终形成了测试报告和单独 bug 单，并把截图放到对应问题下面。 报告给测试留档，bug 单给开发流转，二者分开。

这次流程的问题

  • 一开始把需求疑问问得太泛，问了产品认为“文档已有说明/问题不对”的内容。
  • 早期文档太多，入口分散，测试同学很难知道到底看哪一份。
  • 最初把截图放在问题表外面，不利于开发按 bug 阅读。
  • 没有先固定交付格式，导致 markdown、HTML、报告、问题清单来回切换。
  • “所有状态会员”没有找到充分 UI 证据，后续应在执行前明确需要通过哪个后台页面或接口交叉证明。

以后需要坚持的流程

  1. 先贴需求事实：任务标题、页面路径、原型截图规则、产品补充。
  2. 再列可直接验收的需求点：入口、字段、交互、边界。
  3. 只提出阻塞验收的问题；问题必须绑定到具体字段或交互。
  4. 产品确认后再正式执行测试。
  5. 测试报告只保留一个 HTML 入口。
  6. 发现 bug 后单独出 bug 单 HTML，截图必须放在对应 bug 证据下面。
  7. 每个需求最后更新到总览台账，方便以后快速查。

需要改进的流程

问题 改进规则
问题问得太泛 只问“没有答案就无法判断通过/失败”的问题。不要问架构性、实现性、字段主键类问题，除非它直接影响验收。
文档太散 每个需求只保留一个测试报告 HTML 和一个 bug 单 HTML。中间草稿可以存在，但不作为交付入口。
截图位置不直观 截图必须贴在对应 bug 的证据区，而不是报告底部或单独目录说明。
没有团队系统 用本地/共享 HTML 台账代替系统，先解决“能查、能看、能交接”。

没有测试管理系统时的方案

建议先做一个轻量“测试需求台账”，不用代码仓库也能跑。形式是一个共享文件夹，里面有一个总览 HTML 和每个需求自己的目录。

每个需求卡片显示

  • 需求名称
  • 业务路径
  • 测试状态：待确认 / 待测 / 测试中 / 有 bug / 通过 / 回归通过
  • 问题数量
  • 测试报告链接
  • bug 单链接
  • 最后更新时间

推荐最小字段

字段 用途
需求ID/日期没有系统 ID 时，用日期 + 模块 + 简短名称代替。
需求名称一句话说明测的是什么。
路径后台/H5 点击路径，方便复测。
状态快速看当前卡在哪一步。
风险等级P0/P1/P2 或 高/中/低。
测试报告链接到单需求报告。
Bug单链接到开发用 bug 单。
回归状态未回归 / 回归通过 / 回归失败。
