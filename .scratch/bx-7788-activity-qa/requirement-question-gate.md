# 需求疑问闸门

Status: ready-for-agent

## 目的

防止在需求预期不清楚时直接执行验收测试，导致测试结论把“产品规则未确认”误写成“缺陷”。

## 规则

测试执行前先把问题分成两类：

1. 阻塞型疑问：会改变期望结果、通过/失败标准、数据口径、权限边界或资金/奖励判断。
2. 非阻塞型疑问：不影响当前只读观察，可以边探索边记录。

阻塞型疑问必须先提出，并在确认前只允许做探索性验证，不允许输出正式通过/失败结论。

## 本次 VIP 需求里的阻塞型疑问

- 点击 VIP 成员数量后，成员明细弹窗顶部 VIP 筛选框是否必须显示被点击的 VIP 等级？
- `vipGrade` 是 0 基准枚举、1 基准展示等级，还是后端 VIP 层级主键？
- 成员数量统计口径是否包含冻结、禁用、注销、测试会员？
- 成员数量为 0 时是否允许点击，期望展示空态还是禁用入口？
- 查看会员 tab 未选择 VIP 等级时，默认显示全部、空态，还是最近一次等级？

## 本次可以先执行的非阻塞验证

- 后台是否能进入 VIP 管理。
- `查看会员` tab 是否存在。
- 成员数量字段是否展示为数字。
- 点击成员数量是否能打开成员明细。
- 连续点击 VIP1、VIP2 后，明细总数和行内等级是否明显串用。

这些验证只能说明“页面现状”和“是否存在明显串数据”，不能在需求口径未确认时判定筛选框显示一定是 bug。

## 输出要求

正式测试报告必须区分：

- 已确认需求下的通过/失败。
- 需求未确认下的观察记录。
- 待产品/开发确认的问题。
- 确认后可升级为 bug 的候选项。
